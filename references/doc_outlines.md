# Canonical Outlines

Authoritative section skeletons for the four documents (`topology.md` is generated by `scripts/gen_topology.py` in Phase 1; the other three are scaffolded from `assets/templates/` in Phase 4, and `README.md` is the hub). Specialize every bracketed slot with concrete names harvested in Phase 2 of the workflow. Section order is fixed; numbering may be adjusted if a phase is clearly inapplicable (mark the skip reason in the final handover summary).

## developer_guide.md (15 sections)

1. **Project positioning & scope** — one paragraph on problem domain; bullet list of the headline capabilities.
2. **Metadata snapshot** — license, supported languages/runtimes, dependency list, version source.
3. **Repository layout** — annotated tree of top-level folders and key files.
4. **Runtime architecture overview** — ASCII diagram linking the main data/model/runtime classes.
5. **Top-level namespace** — table of exported aliases vs. real module paths (from `__init__` / `index`).
6. **Backend / platform abstraction (if any)** — unified interface, adapter selection logic, enabled-API registry.
7. **Data & domain layer** — every data container, geometry primitive, constraint/BC/IC type; evidence: sub-package `__init__.py`.
8. **Automatic differentiation / computation core** — how derivatives / gradients / residuals are computed; caching and cleanup contract.
9. **Networks / models catalog** — list of built-in network or model classes with their constructor signatures.
10. **Optimizers & schedulers** — available optimizer names; per-backend/framework adapters; LR-decay matrix.
11. **Training main loop** — step-by-step narrative of the Model/Trainer.compile / .train / .predict / .save / .restore path.
12. **Callback / hook system** — base class lifecycle; enumeration of built-in callbacks and their trigger phase.
13. **Loss & metric registries** — mapping from string identifier to implementation; rules for contributing new ones.
14. **Parallel / distributed training** — what is supported, how to enable, known limitations.
15. **Contribution SOPs & debugging** — dev-env setup, adding a new backend/BC/network, PR flow, common error → root-cause table.

Grounding rules:
- Every section MUST include at least one `path/to/file.py::Symbol` reference the first time it is introduced.
- Sub-package tours (§5–§13) MUST enumerate the real `__all__` list, not a summarized approximation.

## Placeholder conventions

Every template under `assets/templates/` uses the same three placeholder forms. The scaffolder substitutes **only** `{{PROJECT_NAME}}`; everything else is yours to fill in Phase 4.

|Form|Meaning|Handling|
|---|---|---|
|`{{UPPER_SNAKE_CASE}}`|Repo-specific fact to be harvested in Phase 2|Replace with real content; leave the marker in place only if evidence is missing, and list it in the Phase 5 handover|
|`{{NAME_OR_TODO}}`|Fact that may legitimately not exist (e.g. `{{DOCS_URL_OR_TODO}}`, `{{CITATION_OR_TODO}}`)|Replace with the fact, or with `> TODO(doc-miner): <missing fact>` when the repo genuinely lacks it|
|`<angle-bracket slot>`|Free-form hint inside `topology.md` only|Replace with concrete names; never ship a literal `<...>` slot|

Suffix conventions used by the templates:

- `_n` / `_1`, `_2`, … — an indexed series that MUST be enumerated to the count the surrounding prose implies (`{{DATA_1}}`/`{{DATA_2}}`, `{{CAPABILITY_1}}`…, `{{CH6_ITEM_1}}`…).
- `_PATH` / `_FILE` — a repository-relative path, cited in backticks.
- `_SNIPPET` / `_CODE` — a condensed code block (≤ ~30 lines, fence language set).
- `_NARRATIVE` — prose that explains a mechanism, not a list.
- `_SIG` — a real constructor/function signature copied from source.

If a template slot has no counterpart in the target repo (e.g. a PINN-only section in a plain CLI repo), mark the section with a single `> TODO(doc-miner): n/a — <reason>` line and keep the heading, so the document structure stays comparable across repos.
